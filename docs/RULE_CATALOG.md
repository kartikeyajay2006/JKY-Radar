# Rule catalog

Generated from the rule registry 1.0.0 by `npm run docs:matrix`. 157 rules. Rule IDs are immutable; severity is fixed per rule.

Every rule marked tested has a positive case (the rule fires) and a negative near-miss case (it must not fire) in `packages/radar-adapters/test/rule-cases.ts`; `rules.test.ts` fails if a tested rule lacks cases.

| `PROTO_RPC_REMOVED` — RPC method removed | Breaking | A method was removed from a service (a rename is a removal on the wire). | Callers receive UNIMPLEMENTED. | Keep the old method delegating to the new one. | yes |
| `PROTO_RPC_ADDED` — RPC method added | Non-breaking | A method was added to a service. | Additive. | No action required. | yes |
| `PROTO_RPC_REQUEST_TYPE_CHANGED` — RPC request message type changed | Breaking | A method now takes a different request message type. | Existing stubs serialise the old message; fields will be misinterpreted. | Evolve the existing message instead of swapping types. | yes |
| `PROTO_RPC_RESPONSE_TYPE_CHANGED` — RPC response message type changed | Breaking | A method now returns a different response message type. | Existing stubs decode responses into the wrong message. | Evolve the existing message instead. | yes |
| `PROTO_RPC_STREAMING_CHANGED` — RPC streaming mode changed | Breaking | Client or server streaming was added or removed on a method. | Generated stubs have a different call shape; calls fail. | Add a new method with the new streaming mode. | yes |
| `PROTO_MESSAGE_REMOVED` — Message removed | Potentially breaking | A message type was removed. | Source-level breaking for code importing it; Any payloads referencing it cannot be decoded. | Keep the message until no code references it. | yes |
| `PROTO_FIELD_ADDED` — Field added | Non-breaking | A field with a new number was added. | Wire-compatible; old readers skip unknown fields. | No action required. | yes |
| `PROTO_FIELD_REMOVED` — Field removed (number reserved) | Potentially breaking | A field was removed and its number reserved. | Wire-safe, but source-breaking for code using the generated accessor; data is no longer populated. | Confirm no consumer reads the field. | yes |
| `PROTO_FIELD_REMOVED_UNRESERVED` — Field removed without reserving its number | Potentially breaking | A field was removed but neither its number nor name was reserved. | Source-breaking, and a future field may reuse the number, corrupting old data. | Add `reserved <number>;` and `reserved "<name>";`. | yes |
| `PROTO_FIELD_NUMBER_REUSED` — Field number reused | Breaking | A field number previously used by a different field (name and type) now identifies a new field. | Old and new binaries decode each other's data into the wrong field — silent data corruption. | Never reuse field numbers; reserve them. | yes |
| `PROTO_FIELD_RENAMED` — Field renamed (same number) | Potentially breaking | A field kept its number and type but changed name. | Wire-compatible, but breaks generated source code and the JSON mapping. | Keep the name, or accept the source/JSON break explicitly. | yes |
| `PROTO_FIELD_NUMBER_CHANGED` — Field number changed | Breaking | A field kept its name but changed its number. | Old binaries write the old number; new binaries ignore it — data loss. | Never renumber fields. | yes |
| `PROTO_FIELD_WIRE_TYPE_CHANGED` — Field wire type changed | Breaking | A field changed to a type with an incompatible wire encoding (e.g. int32 → string). | Parsers fail or produce garbage for existing data. | Add a new field with the new type. | yes |
| `PROTO_FIELD_TYPE_CHANGED_COMPATIBLE` — Field type changed (wire-compatible) | Potentially breaking | A field changed between wire-compatible scalar types (e.g. int32 ↔ int64, string ↔ bytes). | Decodes on the wire but values may be truncated, sign-converted or invalid UTF-8; source code changes. | Verify value ranges; prefer a new field. | yes |
| `PROTO_FIELD_MESSAGE_TYPE_CHANGED` — Field message type changed | Needs review | A message-typed field now references a different message type. | Compatible only if the two messages are wire-compatible. | Compare the two message definitions field by field. | yes |
| `PROTO_FIELD_CARDINALITY_CHANGED` — Field cardinality changed | Potentially breaking | A field changed between singular, optional and repeated/map. | Readers may keep only the last element or misread packed encodings. | Add a new field instead. | yes |
| `PROTO_FIELD_REQUIRED_CHANGED` — proto2 required changed | Breaking | A proto2 field was made required or stopped being required. | Messages missing the field fail to parse on one side. | Avoid `required`; it can never be safely changed. | yes |
| `PROTO_ONEOF_CHANGED` — Field oneof membership changed | Needs review | A field moved into, out of, or between oneof groups. | Setting one member clears others; moving fields can lose data. | Review oneof semantics with consumers. | yes |
| `PROTO_ENUM_VALUE_REMOVED` — Enum value removed | Potentially breaking | An enum value was removed. | Senders using the value break at compile time; receivers see an unknown number. | Reserve the number and name. | yes |
| `PROTO_ENUM_VALUE_ADDED` — Enum value added | Non-breaking | An enum value was added. | Wire-compatible; old readers treat it as unknown (open enums) — handle defaults. | Confirm consumers handle unknown enum numbers. | yes |
| `PROTO_ENUM_NUMBER_REUSED` — Enum number reused | Breaking | An enum number now belongs to a different value name. | Stored and in-flight values change meaning silently. | Never reuse enum numbers; reserve them. | yes |
| `PROTO_ENUM_VALUE_NUMBER_CHANGED` — Enum value number changed | Breaking | An enum value kept its name but changed its number. | Binary data written by old clients decodes to a different value. | Never renumber enum values. | yes |
| `PROTO_RESERVED_REMOVED` — Reservation removed | Potentially breaking | A reserved field number/range or name was removed. | Re-opens the number for reuse, risking future data corruption. | Keep reservations forever. | yes |
| `PROTO_SYNTAX_UNSUPPORTED` — Unsupported protobuf syntax | Needs review | The file uses syntax/editions or constructs JKY-Radar does not analyse. | Compatibility of those constructs is unknown. | Review manually; do not treat absence of findings as safe. | yes |
